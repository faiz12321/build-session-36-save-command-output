Save command output without replacing an old file

Short answer

The > operator redirects output, but it replaces an existing target. For this practice use Out-File -NoClobber instead, inside a new fictional sample folder. Normal output and errors are separate streams. Windows PowerShell 5.1 Out-File defaults to UTF-16LE; PowerShell 7 Out-File defaults to UTF-8 without a mark. A correctly encoded file is not broken just because another program expects a different encoding.

Follow along with recorded Windows commands. Use PowerShell 7 unless the command explicitly launches powershell.exe for Windows PowerShell 5.1.

Common mistakes

  1. Using > on an existing target. It replaces the file. These exercises use Out-File -NoClobber, which refuses an existing output.
  2. Assuming capture success means the command succeeded. A saved file may be empty or contain an error. Check the native exit code and read what was saved.
  3. Calling valid UTF-16 broken. The receiving program must decode the same encoding. The shown hello bytes are a narrow fixture, not general encoding detection.
  4. Calling text conversion lossless. Get-Content and Out-File can change line endings, final newlines and formatting. Keep originals and compare the actual needed content.

Frequently asked questions

Does > keep an existing file safe?

No. It replaces its target. Out-File -NoClobber refuses an existing target. >> appends instead and can duplicate content when rerun.

Which shell do these commands use?

Run from PowerShell 7 on Windows. One command explicitly launches powershell.exe to test Windows PowerShell 5.1 Out-File. The recorder ran the real programs, not an encoding simulation.

Why are the byte prefixes different?

For this hello fixture Windows PowerShell 5.1 Out-File writes UTF-16LE with FF FE at the start; PowerShell 7 Out-File writes UTF-8 without a BOM by default. This is specifically Out-File behavior, not a claim about every cmdlet or all native redirection.

Does native > behave the same in every PowerShell version?

No. PowerShell 7.4 changed native stdout redirection to preserve byte streams. The practical capture commands here explicitly pipe text to Out-File, not native > byte redirection.

Is the conversion safe for any file?

No. The source encoding is explicitly known for the hello fixture. This line-based text route can change newline details and is not binary-safe or a general encoding detector. Keep the original.
